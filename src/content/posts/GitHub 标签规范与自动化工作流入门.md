## 写在前面

去年我写过一篇文章，讲的是[[大型三维设计项目实战心得：小小的文件命名加速高效创作|文件命名规范]]——那件事给我的启发是：**越是人多手杂的环境，越需要一套规矩来兜底。**

最近我又遇到了类似的问题，只不过场景从三维设计项目换成了 GitHub 仓库。

我的 GitHub 上攒了不少项目，有公开的也有私有的，有大有小，有自己闲来无事写的，也有和远程朋友一起协作的。数量一多，问题就来了：某个 Issue 是修了还是没修？某个 PR 是功能更新还是 bug 修复？过了几个月回来看，翻半天聊天记录才能回想起当时的上下文。

这还不算最要命的。更要命的是，我得手动更新版本号——每次改了点东西，就要想"这次是大版本还是小版本？发版日志写点什么？"——然后经常忘，然后版本号乱跳，然后自己都看不懂了。

说实话，我最初对这些"流程规范"是有点抵触的。总觉得那是大团队才需要的东西，一个人或几个人的小项目，靠"默契"就够了。

直到我被自己的"默契"坑了好几次，才意识到：**好的规范不是给外人看的，是给未来的自己看的。**

于是我开始研究 GitHub 的标签系统和自动化工作流。这篇文章就是这段经历的复盘——不讲具体的配置文件怎么写，而是聊聊背后的思考方式。

## 标签的本质是"分类思维"

在说 GitHub 标签之前，先聊聊更本质的东西：**分类**。

人类天生就爱给东西贴标签。图书馆给书分类，超市给商品分类，甚至你的微信好友分组——本质上都是在做同一件事：**把无序的信息纳入有序的框架，方便后续查找和处理。**

GitHub 的标签（Labels）就是这个道理。每个 Issue 或 Pull Request 都可以贴上不同颜色的标签，一眼就能看出它的"身份"：

- 这是个 bug 还是个新功能？
- 这是紧急的还是可等可缓的？
- 这是前端的还是后端的？

没有标签的时候，你只能一个一个点进去看才知道内容。有标签以后，你扫一眼列表就能掌握全局。

这个场景你是不是很熟悉？这跟你的电脑桌面没有文件夹、你的手机相册没有相册、你的书桌没有抽屉——本质上是一种感觉：**东西多到靠脑力记不住了，需要一个外部的分类系统来帮忙。**

所以 GitHub 标签不是什么高深的技术概念，它就是把"分类思维"搬到了项目管理里。你不需要会写代码，只需要有一颗想把事情理清楚的心。

## 好的规范长什么样

知道要分类了，下一个问题是：**怎么分？**

我踩过的坑告诉我：一开始不要想太多。我第一次搞标签体系的时候，一口气列了二十几个标签，从"性能优化"到"UI调整"到"数据库迁移"——结果呢？真正用上的不到五个，剩下的大部分成了没人看的装饰品。

后来我慢慢总结出三条心法：

### 够用就好

好的规范是从一个具体的痛点长出来的，而不是拍脑袋想出来的。

我的第一版标签只有四个：`bug`、`enhancement`、`documentation`、`question`。这是 GitHub 自带的默认标签，我一开始甚至连这几个都觉得多，只留了 `bug` 和 `enhancement`。

后来发现有些 PR 是纯粹的修修补补，既不算新功能也不算修 bug，于是加了 `chore`。再后来发现有些 Issue 讨论来讨论去没有结论，需要标记一下"悬而未决"，于是加了 `pending`。

**一个标签体系什么时候才算够好？当你需要某个标签的时候，它恰好在。**

### 命名即文档

好的标签名不需要额外解释。

我见过有些项目的标签叫 `A-1`、`B-2`，后面还得跟一份对照表才知道什么意思。这属于本末倒置——标签的作用是降低沟通成本，不是增加沟通成本。

我的原则是：**看到标签名，三秒内能判断该做什么。**

- `bug` → 出问题了，需要修
- `enhancement` → 有新想法，可以讨论
- `help wanted` → 我一个人搞不定，需要帮手
- `wontfix` → 这个我决定先不处理

不需要翻文档，不需要问人，看一眼就懂。

### 颜色传递信息

标签还有一个容易被忽视的属性：**颜色。**

GitHub 的标签可以自定义颜色，这是传递信息的绝佳渠道。

我是这么用的：红色系代表"需要关注"（bug、urgent），绿色系代表"稳定状态"（ready、merged），灰色系代表"未决定"（pending、question）。这样即便你扫过去没看清字，光看颜色就能感知到项目的"健康状态"——一大片红色的项目需要救治，一大片绿色的项目在稳步推进。

## 规范不只是分类，还是沟通语言

标签体系做到这里，其实已经能满足"个人管理"的需求了。但当有其他人加入项目的时候，标签的价值会翻倍——如果你只需要看到颜色的深浅，那么你会觉得"忙不过来"和"轻松好多"是同一回事。

想象一下，你加入一个新项目，打开 Issues 列表，看到的全是没贴标签的条目。你只能一个一个点进去读，猜"这个是不是已经有人在做了？""这个是修完了还是还没开始？"

而一个有标签体系的仓库，你一眼就能看到：
- 这个 Issue 已经被标记为 `accepted`，说明有人已经认可了方向
- 那个 Issue 是 `good first issue`，适合新手练手
- 这个 PR 被标记了 `needs review`，需要有人去审核

**标签体系本质上是一套"共同的语境"。** 它让团队成员不必在每次沟通中都重复一遍 "那个事怎么样了"，因为有标签就够了。

我尤其喜欢 `help wanted` 这个标签。它传达的信息不仅仅是"我需要帮忙"，更是一种态度——"我知道自己搞不定，我欢迎任何人来参与。" 这在开源项目和团队协作中，是一种开放的信号。

## 自动化是规则的延伸，不是炫技

标签贴好了，下一个问题是：**谁来贴？**

你可以手动给每个 Issue 和 PR 贴标签，这当然可以。但就像我前面说的，人总会忘，人总会懒，人总有忙不过来的时候。于是就有了自动化。

自动化在 GitHub 里的角色很朴素：**把反复出现的判断变成条件，让机器替你执行规则。**

举个例子：如果一个 PR 修改了文档目录下的文件，那它大概率属于"文档更新"。这种判断反复出现，每次都手动贴标签，累不累？你完全可以定一个规则："如果改了 docs 目录，自动贴 `documentation` 标签。"这就是自动化最朴素的用法。

再比如版本号的问题。我最初是靠脑子记的——这次改了什么，是大版本还是小版本？结果每次都记混。后来我引入了一个工具，它会阅读我提交时的描述信息，自动判断这次改动的"分量"，然后自动更新版本号。**本质上，我是把一个"我经常搞错"的判断，交给了不会出错的程序。**

自动化不神秘，它就是我们平时说的"写个 SOP，让机器帮忙跑"。区别在于，用标签作为触发器，你可以构建一条清晰的因果链：

> 发生了什么 → 触发哪个规则 → 执行什么操作 → 产生什么结果

这个链条不需要编程思维也能理解，它本质上就是个"如果……就……"的逻辑。而标签，就是那个"如果"的判断依据。

我在这个过程中最大的体会是：**自动化的真正价值不是"省力气"，而是"消除遗忘"。** 人忘贴标签、忘更新版本、忘写发版日志——这些"忘"积累起来就是混乱。自动化把"记住"这件事从人身上剥离了，机器不会忘。

## 从一个小问题开始

回顾整个实践过程，最让我感慨的不是这个系统最终有多顺滑，而是它的起点有多么小。

一开始我只是觉得"版本号老忘记更新很烦"，于是加了一个自动算版本号的工具。然后发现"自动算版本号需要提交信息里有类型标识"，于是开始注意写清楚 `fix:` 还是 `feat:`。然后发现"有了类型标识之后，可以顺便按类型归类 PR"，于是完善了标签体系。然后发现"标签多了之后可以自动贴"，于是加了自动贴标签的规则。

**整个系统是一步步长出来的，不是我一开始就设计好的。**

这跟我在 [[碎片写作——建立一具思维标本|碎片写作]] 里聊到的 Git 设计理念很像：好的系统不是从山顶往下推的瀑布，而是像树一样，从一根树干慢慢长出枝桠。

如果你也想试试，我的建议是：**从你目前最痛的那个点开始。**

- 痛点：总是找不到特定类型的 Issue → 加一个标签分类
- 痛点：老是忘记更新版本号 → 加一个自动版本管理
- 痛点：新人对项目情况一头雾水 → 用标签建立"状态可见性"

不需要一次搞完，不需要追求完美。一个能解决 80% 问题的简单系统，远胜一个完美但没人用的复杂系统。

## 写在最后

写这篇文章，我多少有点忐忑。一方面，标签和自动化在程序员圈子里几乎是标配，拿出来讲显得有些小题大做。但另一方面，我觉得这件事背后藏着一个更通用的道理，和编程无关，和思维有关：

**当你需要管理的东西超过大脑的缓存容量时，你需要一个外部系统来帮你。这个系统可以是一套命名规范、一排文件夹、一组标签，或者任何你定义的规则。**

标签的价值不在于 GitHub，而在于"分类思维"本身。自动化的价值不在于省力气，而在于"消除遗忘"。

最后说一点反思：**规范是服务人的，不是反过来让人服务规范。**

我见过有些项目把标签体系搞得特别复杂，搞得每次开 Issue 都要想半天该贴哪个标签。这就过了。如果贴标签变成了一件有心理负担的事，人就会想方设法逃避它，最后这个规范就形同虚设了。

我的经验是：三个标签起步，顺手再加，勤于修剪。一个太久没用的标签，说明它不够重要，删掉也不可惜。

毕竟，规矩立了是拿来用的，不是拿来供的。
